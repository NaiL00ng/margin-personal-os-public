# ADR 0001：静态原型与未来 Python 后端边界

- 日期：2026-11-08
- 当前决策状态：已采用——保留零外部依赖静态交互原型，并分离模型、交互与动效职责。
- 演进提案状态：待验证——Python 模块化单体方向尚未实现；框架、数据库、部署与迁移细节未选定。
- 关联：[架构概览](../overview.md)、[交互规范](../../design/interaction-spec.md)、[验证记录](../../quality/validation.md)

## 背景

长期目标是具有 Python 核心的个人管理与记账网页工具。当前需要先验证四象限便利贴的交互语义，而真实财务数据、后端同步和账户接入会引入另一组正确性与维护要求。

现有代码仅包含前端状态与本地持久化。将“可操作的原型”标记为“完整个人管理和记账产品”，或者将未来架构写成已经运行的服务，都会误导后续开发和使用。

## 已采用的决策

1. 保留本地 HTML、CSS 和 JavaScript 原型，不为演示交互增加网络依赖。
2. 由 `BoardModel` 负责状态、校验、驻留结算和结束快照；`app.js` 负责浏览器交互和存储适配；`BoardEffects` 负责可关闭的装饰反馈。
3. 完成、取消和调整是不同业务动作。动效不能替代确认，也不能决定动作时间、卡片结果或计时数值。
4. 结束时保留快照，恢复到准备区后继续同一卡片的累计过程；不把恢复理解为擦除旧选择或重写旧快照。
5. 明确使用象限驻留指标，不推定实际工时。保留用户可导出的数据，并提示本地保存异常。

## 待验证的演进方向

Python 后端优先考虑模块化单体：一个部署单元内保留任务、驻留、财务事实、预算计划、承诺回顾和存储适配的明确边界。选择这一方向的理由是减少早期部署和分布式一致性负担，便于围绕个人使用场景迭代；这不是已完成的技术选型。

后续设计须满足以下领域约束：

- **任务与驻留分离**：任务描述用户想做的事，驻留描述卡片所在位置。真实工作会话若加入，应作为另一种事实记录。
- **过程日志与快照分工**：当前日志用于展示过程，结束快照用于保留当次结果。若未来需要任意版本重放，必须补充事件结构，不能宣称当前已经支持。
- **预算与流水分离**：预算是意图和限额；流水是已发生的资金事实。预计收入、目标存款或预算调整不能自动生成已确认交易。
- **关联保持可选**：承诺可关联任务和交易；不要求每笔消费绑定目标，不能把未关联项视作失败。
- **事实先于表现**：后端提交、重复请求处理及数据版本检查独立于前端动画。关闭动画、断网或切换界面不能改变已经确认的业务含义。

## 目前不采用的方向

| 方向 | 当前不采用的原因 |
| --- | --- |
| 立即拆分微服务 | 当前规模和维护需求尚不足以支撑额外的部署、认证和一致性复杂度 |
| 把浏览器本地存储当作长期账本服务 | 缺少完整导入恢复、数据库级并发、跨设备同步与可靠备份机制 |
| 将现有 JS 模型直接称为 Python 内核 | 实现不符；未来需要明确迁移、API 和领域校验责任 |
| 把全部状态统一成“完成” | 会丢失取消与调整的意义，并污染历史记录 |
| 让游戏奖励或动画驱动业务结果 | 视觉反馈应可移除，且不影响保存、计时与恢复 |

## 代价与后续决策条件

静态原型便于离线体验和审查，但无法证明后端能力、真实账单准确性或长期使用效果。未来加入 Python 后端时，部分浏览器逻辑需要移到服务端或重新划分；应避免长期维护两套互相冲突的业务规则。

只有在明确需要服务端持久化、真实交易、跨设备使用或可恢复导入时，才细化后端选型。届时另立决策记录，写清数据迁移、身份认证、冲突处理、账本正确性及部署范围。当前 ADR 不代表任何外部服务已接入，也不自动批准后续数据上传。

## 验证与重新评估

当前模型已有 12 项通过的测试记录，浏览器交互有已执行与未执行的范围区分，见 [验证记录](../../quality/validation.md)。这些检查支持软件行为判断，不证明心理学或管理学效果。

新增后端、改变驻留定义、修改归档恢复语义或引入真实财务数据时，应重新评估本决策。后续实现必须更新状态，不以路线图替代实际完成记录。
