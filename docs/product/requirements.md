## 1. 当前实现基线

当前网页看板已有 Python + SQLite 本机后端，保留独立的静态浏览器存储入口。尚无用户账户、银行连接、真实账本、生命月历或日程同步；数据库基础不等于完整管理与记账产品。

| 能力 | 当前行为与限制 |
| --- | --- |
| 四象限 | 正方形矩阵，重要性／紧急性两个维度；用户主动移动，不自动判断事项重要性 |
| 便利贴 | 名称、可选描述、分类；支持自定义分类；随机外观生成一次，调整与恢复保留外观 |
| 工作台 | 新建、准备区、调整、完成、Void；拖拽之外可用卡片详情按钮操作 |
| 调整 | 进入编辑时暂停驻留并暂留卡片；保存或关闭窗口后回准备区；取消只放弃文字修改 |
| 结束与恢复 | 完成和取消分开记录；保存当时的内容、外观和时长快照；恢复到准备区，不抹去既有归档 |
| Void | 拖入并停留 1.2 秒后松手确认；移开或提前松手不取消；详情页另有明确确认按钮与可选原因 |
| 驻留 | 按卡片所在象限的墙钟时间分别累计，准备区与编辑期间暂停；关闭页面期间仍从保存时间戳续计 |
| 动效 | full／reduced／off 三种强度，默认尊重系统减少动态效果偏好；装饰性随机不影响业务结果 |
| 保存 | Python 入口使用本机 SQLite；静态入口使用独立浏览器存储。确认保存、等待与结果待确认分别提示，不跨设备同步 |
| 数据与备份 | 数据库模式支持 JSON 预览后合并导入、手动备份与预览后恢复；恢复替换领域记录，先自动备份当前状态 |

实现与验证不是同一状态。浏览器、模型／后端测试及未完成验证的准确范围以 [验证记录](../quality/validation.md) 为准；本文件不将静态代码审查或设计推演报告为实际测试通过。

## 2. 拟议页面结构

以下是完整产品的信息架构提案。首版可以用一个页面中的分区或抽屉承载，导航名称不要求对应独立页面。

| 页面／入口 | 主要问题 | 内容与操作 | 当前状态 |
| --- | --- | --- | --- |
| 首页／生命月历 | 我处于怎样的阶段，这个月想把什么留下来？ | 每月一格；过去月份的经历与成果；当前月份的重点；未来月份的规划；进入某月详情 | 未实现，MVP 提案 |
| 行动看板 | 下一步做什么，哪些事项需要调整？ | 四象限、准备区、操作工作台、卡片详情；后续关联目标、项目和行动计划 | 核心交互与本机持久化已实现；关联与计划未实现 |
| 项目详情 | 为这件事准备了多少资源，实际发生了什么？ | 目标理由、任务与日程、时间计划／实际、预算预留／实际收支、成果与回顾 | 未实现，联动 MVP 核心 |
| 资金页面 | 账是否可信，近期有哪些实际收支和未来承诺？ | 账户、交易、待核对项目、预算预留、与项目的关联；数据覆盖说明 | 未实现 |
| 回顾与记录 | 哪些选择值得保留、调整、暂停或结束？ | 完成／取消历史，月度回顾；预期与体验的可选对照；下一步行动 | 归档记录册已实现；综合回顾未实现 |
| 设置与数据 | 如何控制体验并保管自己的资料？ | 动效、颜色、数据来源说明、导出、旧记录导入和本机备份；后续评估权限设置 | 数据库入口已实现导入、备份与恢复；无账户权限系统、定时备份或同步 |

生命日历是首页的重要视图，但不能阻挡直接新建、记账或查看下一步。待录入和待核对事项可通过相应页面入口处理；不另造一套相互冲突的待办清单。

## 3. 领域对象与独立的事实维度

| 对象 | 语义 | 关键约束 |
| --- | --- | --- |
| 价值／目标 | 使用者在意的方向与希望达成的结果 | 可选、可调整；不是人格评分；未关联目标的事项仍可使用 |
| 项目／生活事项 | 连接任务、时间、费用与成果的共同语境 | 先用明确的关联关系，不要求所有日常交易属于项目 |
| 任务卡片 | 可行动事项及其位置与状态 | 完成不等于已付款；取消不等于删除事实；允许调整与恢复 |
| 日程／时间计划 | 未来安排或预留的时间段 | 属于计划，可以改期与撤销；不自动算作实际投入 |
| 实际时间记录 | 用户明确记录的已发生投入 | 与计划及驻留分开；来源可以是手动记录或未来明确启停的计时功能 |
| 象限驻留 | 卡片处于某象限的累计墙钟时间 | 多卡可同时累计；不能用于推断专注、工时、效率或活动是否发生 |
| 预算预留 | 对现有或预期资源的计划分配 | 不是交易，不直接改变账户的实际余额；若依赖预期收入须明确标记 |
| 实际交易 | 已确认的收入、支出、转账或退款事实 | 金额、币种、账户、发生日期与来源可核查；不由卡牌动画创建或修改 |
| 成果／回顾 | 对已发生经历的记录与主观评价 | 主观评价与财务事实分开；不强制逐笔评分；空白不解释为负面评价 |

时间与金额分别计算并列呈现。金额不得采用会产生舍入误差的随意浮点累计；未来实现应使用明确的最小货币单位或 Decimal，并保留币种。MVP 不把不同币种直接相加，也不默认把时间按工资换算成金钱。

首版项目关联宜保持简单：一条记录可不关联项目，或关联一个项目。若以后支持拆分，应以分摊记录保证金额和时间不被重复统计，而不是仅添加多个标签后在各项目全额相加。

## 4. 模块需求与研究边界

### 4.1 生命月历与目标导航：下一步提案

- 一个方格代表一个自然月，具体起点与展示范围由使用者选择；未来方格明确是规划，不是预测。
- 点击月份能看到相关经历、已完成事项、主动取消的选择和简短回顾；与项目、任务、费用之间的关联可追溯。
- 不以花费、工时或完成件数自动给月份上好坏颜色。没有记录的月份表示“未记录”，不能标记为失败。
- 允许用一句话描述本阶段在意的目标，也允许跳过目标设置直接使用工具。
- 概念依据是有限性、未来自我连续性、自我一致目标与时间视野。生命月格这一具体界面是否产生积极效果，仍待验证。

### 4.2 动态矩阵与行动计划：现有基础上扩展

- 保留四象限、拖拽反馈和按钮替代操作；重要性由使用者表达，并可附一条简短理由。
- 后续期限字段应区分真实外部截止、本人期望日期和机会窗口；不通过伪造紧迫性推动操作。
- 可选的下一步计划应足够具体，例如“周二早餐后先写十分钟提纲”，不要求所有卡片填写长表单。
- 若未来提出象限迁移或优先级建议，必须说明原因、允许覆盖，且不能未经确认改写用户的价值判断。
- 当前“动态”指交互及状态变化。自动排程、期限驱动迁移和智能优先级均不属于当前实现。
- 方法依据为紧迫性偏差、实施意图及进度监测；这些研究不直接证明四象限界面优于普通清单。

### 4.3 卡牌、结束语义与可逆操作：保留现有核心

- 完成：停止当前驻留，保存当次归档快照，进入已完成记录。
- Void／取消：停止当前驻留，保存取消快照与可选原因，进入独立记录；不统计为“失败”。
- 调整：保留身份、外观与历史，编辑期间暂停并暂留，保存或关闭后回准备区；取消仅放弃文字修改。
- 恢复：回准备区，继承累计记录，保留此前结束事件；重新进入象限才开始新一段驻留。
- 长期的“项目暂停”与当前“卡片移到准备区”不同。前者尚未实现，不应只改名称就宣称已有完整暂停系统。
- 动画用于解释操作与提供体验，关闭后所有功能仍可用；保存、计时和状态提交不依赖动画播放完毕。
- 自主性、能力感与游戏化研究提供设计线索；本原型的动效对长期行动或习惯的效果仍是待验证假设。

### 4.4 基础记账：下一步提案

首版聚焦少量手动账户与单一币种，支持收入、支出、内部转账和退款的明确语义。复杂投资估值、借贷计息、税务和多币种折算不纳入首版承诺。

| 痛点假设 | MVP 设计方向 | 不可省略的约束 |
| --- | --- | --- |
| 每笔都填很多字段导致放弃 | 最少必填字段、上次选项复用、可选项目关联；其余信息渐进补充 | 不能为了省步骤省掉金额、币种、账户与日期的基本可核查性 |
| 同一交易重复记录或难以核对 | 明确来源、待核对状态、编辑历史；在增加导入后提供预览与去重候选 | 不能仅凭相似金额自动删除或合并交易 |
| 看到账目感到负担或回避 | 提供中性摘要、分批核对、稍后继续；不使用责备语气 | 不能隐藏已知事实；缺失和未核对必须可见 |
| 图表很多但不知道如何调整 | 将交易与项目目标、预算预留和可选回顾关联 | 不把每次消费都转化成道德判断，也不提供无依据的个性化投资建议 |

“繁琐”和“回避”在此是需要在目标使用场景中验证的痛点，不是假定每个人都具有的心理特征。方法依据与可外推边界见 [研究证据登记表](../research/evidence-register.md)。

账本最小正确性要求：

1. 初始余额与后续交易分开；账户余额由可解释的记录计算，缺少初始信息时不得展示貌似完整的结论。
2. 内部转账不是收入或消费；退款关联原支出或明确列为待核对退款，不将其误计为新的劳动收入。
3. 预算预留只改变计划可用额度，不改变实际余额；预留和实际支出不能简单相加为“总花费”。
4. 实际交易允许纠错，但应保留变更痕迹；取消项目不撤销已发生支出，收到退款才新增相应事实。
5. 每个摘要说明覆盖时段、账户、币种、待核对数量与数据缺口；不把没有录入解释为没有消费。

### 4.5 双资源项目页：MVP 的主要联动

项目页并排呈现四类信息：计划时间、已记录实际时间、预算预留、已确认实际收支。象限驻留作为过程信息单列，不进入实际时间合计。

- 创建一个目标或生活项目时，可以分别预留时间与预算，也可以只填写一种资源。
- 完成任务仅更新任务状态；付款只有经用户确认或可靠来源核对后才成为交易。
- 日程到期不自动变成已投入；交易发生也不自动证明课程上完、旅行实现或目标达成。
- 调整或取消项目可以释放未发生的日程安排与预算预留；已经发生的投入、支付和历史选择继续保留。
- 提供“保留、缩小、暂停、结束”的项目回顾方向；其中项目级状态管理尚未实现。
- 机会成本与跨期选择是方法依据；“时间与金额一起看能改善决策”仍是需要验证的产品假设。

### 4.6 本机记录基础：首版已实现

- Python 入口的新数据库为空，静态入口保留原示例；不能自动把浏览器旧数据当作用户同意导入。
- 「数据与备份」先展示导入预览和问题，再由用户确认合并。保留卡片 ID、外观、位置、累计与已有结束快照；冲突和异常明确拒绝，不静默丢记录。
- 旧累计作为历史基线，缺失过程保持未知；导出时的派生统计不再次累计。导入记录不等于导入账单，仍没有财务模块。
- 请求重试不重复结算或结束；其他标签改变记录时提示版本冲突，不静默覆盖。结果未知时不能误报成功或确定失败。
- 恢复备份是替换当前领域记录，不是 JSON 合并；先预览并明确确认，且自动保留恢复前安全备份。
- 持久化支持可核对的过程记录，研究关联见证据登记 E03／E05／E07；事务和备份的工程正确性由测试验证，不以论文或存储方式证明产品的行为效果。

## 5. 典型流程

以下数字均为合成示例，不描述任何真实使用者的财务或行为。

### 流程 A：从一个念头到一次完成

1. 在准备区创建“写出提纲”，可选关联“学习项目”。
2. 用户依据自己的理由放入第二象限，卡片开始累计第二象限驻留。
3. 后续 MVP 可添加“周二早餐后写十分钟”的行动计划；计划与驻留各自保存。
4. 用户确认完成，卡片结束并播放所选强度的动画，记录册保留快照。
5. 后续生命月历显示该成果入口；不会仅因完成卡片而生成实际工时或支出。

步骤 1–2 的基础卡片操作及步骤 4 已实现；项目关联、行动计划和步骤 5 尚未实现。

### 流程 B：课程同时占用时间和金钱

1. 新建学习项目，计划十小时、预留 CNY 1,000；二者都是计划。
2. 报名支付 CNY 800 后确认实际支出，并关联该项目；剩余预留由用户决定保留还是释放。
3. 参加课程后，用户明确记录实际投入；任务完成与时间记录分别确认。
4. 项目页并列展示计划／实际的两种资源，不合成单一“投入分”。
5. 回顾时可自愿判断课程是否符合最初目的，再决定继续或调整。

此流程为联动 MVP 提案，当前原型未实现。

### 流程 C：暂停或取消，不抹去事实

1. 用户决定暂停课程，保留项目背景，撤销尚未发生的日程安排。
2. 系统提出释放未使用预留的选项；实际已支付 CNY 800 保持不变。
3. 若后来收到 CNY 300 退款，明确新增并核对退款事实，不通过修改卡片状态伪造退款。
4. 重返时显示下一步行动与现有资源信息，不要求补齐暂停期间所有记录。

项目级暂停、预算与退款均为后续提案；当前仅有卡片准备区、取消和恢复语义。

### 流程 D：中断记账后的重返

1. 用户回来后先看到数据覆盖截止时间与待核对项，不看到惩罚性的断签提示。
2. 可以选择先记录今天，或分批补充过去的事实；历史缺口继续标记为未知。
3. 若未来提供账单导入，先预览来源、范围和去重候选，经确认后再写入账本。
4. 简短回顾只提出一个可执行的调整，不强制完成完整的自我分析。

此流程尚未实现；便利性、理解程度与回避感变化都需验证。

## 6. 非功能要求与数据边界

- 数据库模式由 Python 确认业务状态及动作时间，网页负责交互和展示；静态入口保留原模型。状态迁移和保存不由视觉效果决定，未来账本仍需独立验证。
- JSON 导出／合并导入与 SQLite 备份／替换恢复语义不同；操作说明见 [后端指南](../backend-guide.md)。当前仅支持数据库 schema 1，未知版本拒绝打开，未来迁移尚未实现。
- 保存失败、来源冲突、导入异常必须清楚告知，不能显示未实际保存的成功状态。
- 当前没有离线写入队列、跨设备同步、持久表单草稿、定时备份、数据加密或公网账户；本机备份不等于异地灾备。
- 键盘、触屏和减少动态效果应有可用路径；窄窗口检查不等于真实触屏兼容性已经通过。
- 任何联网集成、自动发送、上传个人数据或外部分析都须有明确用途和相应授权；代码仓库仅含代码、文档与合成示例。
- 默认不加入用于提高黏性的强制通知、随机奖励或羞辱排行；提醒频率和回顾节奏由用户控制。

## 7. 待验证假设与验收方式

以下是验证设计，尚未执行为本产品的效果试验，也未设定虚构的成功率或上线日期。

| 假设 | 主要观察 | 反向信号与处理 |
| --- | --- | --- |
| 月格能帮助有意义的回顾 | 是否能从回顾形成并落实本人认可的下一步 | 只增加压力或装饰性浏览时，减少默认展示频率与内容 |
