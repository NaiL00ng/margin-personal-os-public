# 产品能力路线图

- 文档日期：2026-11-08
- 状态：阶段性能力提案，不是交付承诺或执行任务台账。
- 当前基线：`0.3.0-dev.2`，本机后端、数据导入与备份恢复，以及可本机构建的 macOS 启动器。
- 本路线图不设置未经确认的日期、负责人、工作量或完成比例。
- 关联：[愿景](vision.md)、[需求与交互语义](requirements.md)、[研究证据登记表](../research/evidence-register.md)、[当前原型](../../README.md)。

## 1. 阶段与现状

阶段描述产品在什么条件下具备下一层能力，不表示已经批准逐项开发。研究、技术方案和使用反馈可以改变顺序；只有达到相应验收条件后，才能更新能力状态。

| 阶段 | 希望形成的能力 | 目前状态 |
| --- | --- | --- |
| A：交互原型基线 | 以正方形矩阵和卡牌体验验证状态与反馈是否清楚 | 核心原型已实现；兼容性与长期体验仍有未验证范围 |
| B：可靠的单人产品基础 | 网页端与 Python 内核协作，记录能正确保存与恢复，版本边界明确 | 本机首版已实现；未来 schema 迁移与更广兼容性尚未完成 |
| C：管理与记账联动 MVP | 用一个项目连接任务、时间安排、基础账本和预算，加入基础生命月格 | 未实现，下一步主要产品范围提案 |
| D：降低日常维护成本 | 可核对的导入、重复记录复用、适度日程集成和中断后重返 | 长期提案 |
| E：可解释的个人决策支持 | 人生章节、情景比较、预期与实际回顾、谨慎的辅助建议 | 长期探索，不承诺全部实现 |

## 2. A：交互原型基线

当前已有四象限、准备区、事项创建与分类、拖拽及按钮操作、调整、完成、Void、归档与恢复、逐象限驻留、三档动效和本地导出。

这一阶段的产出是可操作的交互原型，不是完整个人管理与记账产品。生命月历、实际工时、日程系统与账本仍未实现；Python 存储基础在阶段 B 中记录。

保留的验收标准：

- 正方形四象限布局及重要性／紧急性语义可辨认。
- 拖拽成功落位才改变状态；无效落点和中止不丢卡、不重复结算。
- 编辑暂停并暂留，保存、取消或关闭后均回准备区；取消只放弃文字修改，时间语义一致。
- 完成与取消保留不同快照；恢复不覆盖历史。
- Void 需要明确的确认动作；停留或确认取消时不产生意外状态变化。
- full／reduced／off 具有相同业务结果；随机仅发生于美术。

验证事实集中在 [验证记录](../quality/validation.md)。已有模型测试或部分浏览器操作不代表持续使用、全部拖拽手感及跨设备兼容性已验证。

## 3. B：可靠的单人产品基础

目标是让使用者能够信任自己的记录，并为联动 MVP 提供稳定基础，而不是先扩充大量图表。

首版已实现：

- Python 3.9+ 标准库本机服务与 SQLite；网页继续展示和交互，静态入口保持独立浏览器存储。
- 卡片、事件、快照、分类、设置和驻留区间持久化；事务、幂等请求与全局 revision 处理重复动作和并发冲突。
- 旧 JSON 预览后合并导入、手动 SQLite 备份与预览后恢复；恢复前自动保留当前库，缺失历史明确未知。
- 服务端动作时间用于驻留结算，编辑进入准备区；原动效三档、按钮及键盘替代操作保留。
- 区分保存确认、结果待确认与冲突；待确认重试不是离线队列，数据库不可用时不静默降级为浏览器保存。

仍未实现：未来 schema 迁移、离线写入队列、跨设备同步、持久表单草稿、定时／异地备份、加密及公网账户。当前只支持 schema 1，未知版本拒绝打开。这些能力需要按实际需要另行确定范围，不是本版承诺。

进入下一阶段的条件：

- 典型创建、移动、编辑、结束与恢复流程不会造成记录丢失或重复累计。
- 从备份恢复后的身份、内容、归档和统计可核对；错误恢复不会静默覆盖原记录。
- 用户能够辨认“已保存”“仅在当前页面”“需要处理冲突”等状态。
- 新增内核与存储路径经过相应测试；尚未完成的兼容性范围明确记录。

这些条件需要持续由实际测试与使用核对，不能因首次实现而视为所有设备和故障都已验证。详见 [后端指南](../backend-guide.md) 与 [ADR 0002](../architecture/decisions/0002-local-sqlite-backend.md)。此阶段并不要求先做多人协作、社交功能、公共分享或复杂云同步；后续项目、实际时间和交易仍保持独立语义，不把驻留改名为工时。

## 4. C：管理与记账联动 MVP

最小完整体验是：使用者选定一件在意的事，为它安排时间与预算，记录实际发生的投入，最后可以完成、调整、暂停或取消，并在月份中回看这一选择。

### 纳入范围的提案

| 能力 | MVP 边界 |
| --- | --- |
| 目标与项目 | 简短的目标理由与项目关联；可跳过，不要求完整人生分类体系 |
| 行动 | 延续现有矩阵、卡牌、准备区与归档；增加可选的具体下一步 |
| 基础生命月格 | 每月一格，查看相关成果与回顾；未来月份明确为计划；不预测寿命 |
| 时间 | 分开记录计划时段、明确记录的实际投入与象限驻留；不自动把日程完成当工时 |
| 基础账本 | 单一币种、少量手动账户、收入／支出／转账／退款的正确语义；不包含复杂投资与税务 |
| 预算 | 预留与实际独立，取消未用预留不删除已发生交易 |
| 双资源项目页 | 并列展示时间和金额，区分计划与实际；单条记录的项目关联避免重复统计 |
| 简短回顾 | 可选择保留、调整、暂停或结束；可选记录预期与体验，不强制逐笔反省 |

### 暂不纳入首版承诺

- 银行直连、自动支付、自动对外发送资料或建议。
- 多币种汇兑、投资绩效、税务计算与复杂借贷产品。
- 基于行为数据推断心理状态、人格或道德评价。
- 自动替用户决定重要性、自动优化人生安排、寿命预测。
- 连续签到惩罚、随机奖励倍率、排行榜与以使用时长为目标的设计。

### 开发前与验收条件

每个模块先形成可追溯的证据卡，并在 [证据登记表](../research/evidence-register.md) 中区分机制研究、界面外推和本产品假设。证据不足的部分可以进入明确标注的探索性验证，但不写成“研究已经证明本产品有效”。

联动 MVP 至少应验证以下完整流程：

1. 同一项目分别预留时间与预算，用户能解释它们为何不是实际投入。
2. 实际付款与实际时间记录独立确认，不因卡片完成而伪造事实。
3. 转账不被计为收入或消费，退款有明确来源和核对路径。
4. 项目暂停或取消后，未发生承诺可以释放，已发生投入仍然保留。
5. 月度回顾能追溯到相关记录；空白、缺失与待核对不会显示成零发生。
6. 中断后可以继续使用，不必先补齐所有历史记录。

## 5. D：降低日常维护成本

只有基础账本与联动语义可靠后，才扩大录入来源与自动化程度。

可选能力包括账单文件导入、重复交易模板、日程读取与关联、分批核对、数据覆盖提醒，以及按实际需求评估的跨设备使用。它们不预设必须接入某一家外部服务。

每项新来源应说明授权范围、数据流向、写入或只读权限、错误处理与退出方式。导入需要预览、来源标识、重复候选和可追溯的确认过程；不能把相似交易直接自动合并。识别或分类建议不确定时应保留待核对状态。

进入更复杂支持的条件是：维护步骤确实减少，同时账目错误、数据缺口或回避负担没有恶化。更多自动化不自然等于更好的体验；若自动化造成难以核对，应缩小范围。

## 6. E：可解释的个人决策支持

长期可探索的方向包括：

- **人生章节与未来自我。** 从月份汇总为用户自己命名的阶段，连接目标、经历和关系；不按年龄规定应该达到的成就。
- **资源情景比较。** 比较继续、缩小、暂停某项目时，未来时间安排和预算预留如何变化；明确显示假设，不伪装成预测。
- **预期与实际回顾。** 在低频、自愿回顾中比较最初期待与实际体验；不把每次消费都纳入心理评分。
- **可解释建议。** 如果以后使用规则或模型提出建议，应展示依据、不确定性和替代选项；用户保留最终选择。
- **个人使用实验。** 比较不同提示、动效或回顾节奏是否适合本人，评价真实行动与负担；个人结果不自动推广为普遍科学结论。

这些是研究方向，不是已经确定的功能清单。不能以“别人没做过”为准入标准，也不能因一个功能听起来新颖就跳过研究和验证。

## 7. 贯穿各阶段的验证原则

| 层次 | 要回答的问题 | 不可替代的界限 |
| --- | --- | --- |
| 数据正确性 | 金额、时间、状态与恢复是否符合定义？ | 动效好看或用户喜欢不能弥补事实错误 |
| 可用性 | 用户是否理解计划／实际、完成／取消、保存／未保存？ | 点击成功不代表理解正确 |
| 日常负担 | 录入、核对和中断后重返是否容易？ | 低录入时间不能以隐藏缺失数据为代价 |
| 个人价值 | 是否支持本人认可的重要行动与资源选择？ | 更多打开、更多完成件数不等于更好的生活结果 |
| 行为效果 | 改善是否持续、是否存在反向影响？ | 短期满意度和单人试用不能证明普遍因果效果 |

下一轮验证可以采用先观察现有行为、再进行有界试用的方式，并预先定义关心的结果与负担信号。样本、时长、指标阈值和结论范围需要实际确定；本文件不将尚未执行的验证写为通过。

阶段可以缩小或回退：若出现错误余额、误取消、无法恢复、明显回避或为了奖励而刷任务，应优先修复相关机制，再决定是否继续扩展。产品能力是否进入下一阶段，依据的是可检查的结果，而不是日历上的预设日期。
